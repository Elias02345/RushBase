# Scale test: 100 000 assets / 50 TB (2026-10)

Acceptance of milestone M7 (spec section 16): search p95 below 500 ms with 100 000 assets and
50 TB on a 4-core CPU server, no GPU. This page records the rig, the numbers before and after the
tuning, the changes and what is left.

## Rig

| Part | Setting |
| --- | --- |
| Catalog | `scripts/perf/seed.py`: 100 000 assets (70 % video with 3-20 shots, 20 % photo, 10 % audio), 802 900 shots, 665 000 tags in 6 taxonomy fields, 528 000 transcript segments (30 % of the videos), 1 224 247 SigLIP image vectors, 1 086 097 e5 text vectors (clustered, L2-normalised, 768-d), 200 000 audit entries, 48 open needs items, `size_total` sums to 50.0 TB |
| Load time | 4 minutes for all rows (COPY, binary COPY for the vectors); HNSW builds 14 + 9 minutes (3 parallel workers) |
| Database size | 27 GB with full-precision HNSW (index 4.8 + 4.2 GB), 21 GB with the halfvec indexes of migration 0007 (2.4 + 2.1 GB) |
| PostgreSQL | `pgvector/pgvector:pg16` in a container with `--cpus=4 --memory=8g` (a deliberately small RAM budget: the database is three times larger than RAM). "Before": stock settings (`shared_buffers` 128 MB). "After": the settings now shipped in the compose files (`shared_buffers` 2 GB here, 1 GB default, `work_mem` 16 MB, `random_page_cost` 1.1, `jit` off) |
| Server | `rushbase-server` pinned with `taskset -c 0-3`, real ONNX text towers (SigLIP 2 text fp16, multilingual-e5 int8, 2 threads) |
| Client | `scripts/perf/bench.py`, pinned to cores 4-7; "one client" = 30 requests per endpoint class in sequence; "8 clients" = 60 s of the weighted mix |

Reproduce:

```sh
docker run -d --name rushbase-perf-pg --cpus=4 --memory=8g --shm-size=5g -p 127.0.0.1:15433:5432 \
  -e POSTGRES_USER=rushbase -e POSTGRES_PASSWORD=perf -e POSTGRES_DB=rushbase_perf pgvector/pgvector:pg16
uv run python scripts/perf/seed.py --admin-url postgresql://rushbase:perf@127.0.0.1:15433/postgres
RUSHBASE_MODELS_DIR=<worker data dir>/models uv run python scripts/perf/bench.py \
  --db-url postgresql+psycopg://rushbase:perf@127.0.0.1:15433/rushbase_perf --label after \
  --report docs/eval/2026-10-perf.md
```

## Verdict

* Search p95 is under 500 ms for a single user at 100 000 assets, for asset and scene search, and
  all list, facet, detail, statistics and needs endpoints are far below the budget.
* **Not met on this rig:** hybrid search *with several filters* (796 ms) and any search with eight
  users hammering four cores (700-1700 ms). Both are dominated by cold index pages: the working
  set (two HNSW indexes of 4.5 GB plus the 14 GB of vectors a selective filter has to read) is
  larger than the 8 GB container. Warm, the same queries take 60-130 ms (`EXPLAIN ANALYZE`
  examples below). With 16 GB of RAM or more, or the `shared_buffers` advice in
  `docs/operations.md`, the filtered case fits. Eight users that all search at the same instant
  need more than four cores for the two ONNX encoders alone.
* Nothing was weakened to get these numbers: results are exact except the documented ranking
  pool (below).

## What was slow and what changed

| Finding (EXPLAIN / slow log) | Change |
| --- | --- |
| Every search ran `count(*)` over a million vectors twice to find out whether compatible vectors exist | `hybrid.has_compatible`: an `EXISTS` probe; the capabilities endpoint caches the counts |
| The encoder ran inside the event loop and loaded lazily (first query 3.8 s) | Encoding in a worker thread, an LRU of 512 query vectors, background warm-up at start (`/search/capabilities` shows `warming`, `/health` reports `encoders`) |
| Full-text ranking of a common word over all 800 000 shots / 528 000 segments took 1-1.6 s | Only a pool of 5000 matches (`RANK_POOL`) is ranked; rarer terms are still ranked completely |
| 13 enum facets = 13 table scans, 6 tag facets = 6 more | `GROUPING SETS`: one pass for all facets without an active own filter, one extra pass per active filter; tag counts in one pass |
| Statistics did four scans | One grouped scan |
| Sorting the list by date, size, duration, created: sequential scan plus sort (195 ms for the first page) | Four keyset indexes `ix_asset_sort_*` (0.3 ms) |
| Tag filter as a correlated `EXISTS` over three tables inside the HNSW scan | Semi-join on the resolved value ids: 3x faster warm, 3x cold |
| HNSW indexes of 4.8 + 4.2 GB did not fit in memory | HNSW on `embedding::halfvec(768)`: 2.4 + 2.1 GB, same plans, same recall in practice |
| Needs matching ran one hybrid search per open item for every asset (9 s median) | The searches of an item are shared by all assets of a filing burst (TTL cache); the query vectors come from the LRU |
| Default PostgreSQL settings (128 MB `shared_buffers`, JIT on) | Tuned flags in both compose files, `ALTER DATABASE ... SET` for bare installs |
| Aggregates recomputed under load | `TtlCache`: shared computation, stale-while-revalidate, `RUSHBASE_QUERY_CACHE_SECONDS` (default 15, 0 = exact) |
| No upper bound for a query | `RUSHBASE_STATEMENT_TIMEOUT_SECONDS` (default 30) |

Measured but not changed: HNSW `ef_search` stays 200 with iterative scans in `relaxed_order` (lowering it
did not change the warm times); `hnsw.max_scan_tuples` keeps pgvector's default.

Examples (`EXPLAIN (ANALYZE)`, 1.2 M vectors): unfiltered text-vector channel 74 ms warm / 675 ms
after a restart with cold caches; the filtered one 107 ms warm; first list page sorted by date
195 ms before the index, 0.3 ms after.

## Recommended sizing

See `docs/operations.md` (section "Sizing"). In short for 100 000 assets: 4 cores, 16 GB RAM (8 GB
works but filtered semantic searches are then disk-bound), 40 GB of fast disk for PostgreSQL
(21 GB measured plus WAL and backups), `shared_buffers` 25 % of RAM.

## Migration cost

Migration 0007 rebuilds the two HNSW indexes on halfvec. For 2.3 M vectors that took about 25
minutes at `maintenance_work_mem` 1 GB; small catalogs take seconds. The migration is idempotent
and runs before the server starts (the installer and updater run it with the service stopped).
